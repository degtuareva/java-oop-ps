В текущем коде одновременно решаются задачи UI, бизнес?логики и работы с базой, поэтому он получается «тяжёлым» и трудно сопровождаемым. Ниже краткий отчёт по основным проблемам.

1. Отсутствие слоёв и нарушение Single Responsibility
   Класс Main отвечает сразу за:

взаимодействие с пользователем (меню, Scanner, вывод сообщений);

управление сессией (isLoggedIn, isAdministrator, loggedInUserId);

бизнес?логику (права администратора, выбор автора статьи);

вызовы к базе через объект D.

Класс D одновременно:

инициализирует схему БД (initializeDatabase);

работает и с пользователями, и со статьями, и с ролями, и с паролями.

Это прямое нарушение принципа единственной ответственности: один класс должен меняться по одной причине, а не по десятку разных (изменить схему БД, сменить формат меню, поменять логику авторизации и т.д.). В результате любое изменение (например, в логике пользователей) тянет правки в больших «божественных» классах, что увеличивает риск ошибок.?

2. «God?class» и процедурный стиль
   Main и D фактически являются «god?class»/«god?object»: в них сосредоточено слишком много несвязанных по смыслу методов и данных.?

Огромный switch в main с кучей кейсов.

Множество статических методов в Main, которые используют глобальное состояние (isLoggedIn, loggedInUserId).

D оперирует сразу всеми сущностями (User, Article, роли, пароли), то есть потеряна связность (cohesion) и нарушены границы между предметными областями.

Это усложняет понимание: чтобы проследить сценарий «добавить статью», приходится переходить между main, несколькими статическими методами и методами класса D. Подобные структуры относятся к типичным code smell?ам и считаются анти?паттернами в промышленном коде.?

3. Глобальное состояние и статические утилиты
   Состояние сессии (isLoggedIn, isAdministrator, loggedInUserId) — статические глобальные поля.

Методы Main — статические и завязаны на эти глобальные переменные.

Глобальное состояние затрудняет тестирование и сопровождение: любая функция может изменить общий флаг, и отследить, кто именно это сделал, сложно. Кроме того, такие функции нельзя удобно переиспользовать в другом UI (например, веб?контроллер), потому что они жёстко завязаны на Scanner и общем состоянии.?

4. Смешение UI и бизнес?логики
   В методах вроде addArticle, deleteArticle, addUser, changeUserPassword одновременно выполняется:

чтение ввода пользователя (работа с Scanner);

бизнес?решение (какие поля брать, кто автор, можно ли менять);

вызов конкретного SQL?метода D.

Такое смешение приводит к тому, что:

нельзя протестировать бизнес?логику отдельно от консоли;

невозможно переиспользовать логику с другим интерфейсом (например, REST API).

Рекомендация: разделять слой представления (UI), сервисный слой (бизнес?логика) и слой доступа к данным (DAO).?

5. Плохая читаемость и слабая выразительность API
   Названия методов класса D и Main сокращены до аббревиатур: cu, gubu, ga, da, addArticle(D database) и т.д.

Такие имена не отражают назначение методов, нарушают принцип самодокументируемого кода и усложняют вход в проект для нового разработчика.?

Кроме того, Main содержит дублирующиеся по смыслу методы (createArticle, addArticle, viewArticles, viewAllArticles, listAllArticles), что затрудняет понимание, какой метод действительно используется и где. Это увеличивает риск расхождений в поведении.

6. Жёсткая связность и отсутствие инверсии зависимостей
   Вызовы к базе данных выполняются напрямую через DriverManager.getConnection внутри методов D и завязаны на конкретные строки подключения (jdbc:postgresql://localhost:5432/oopshop, логин/пароль).

Main напрямую создаёт D и работает именно с этим классом.

Это нарушает принципы инверсии зависимостей и затрудняет:

подмену реализации БД (например, на H2 в памяти для тестов);

внедрение моков/фейков при тестировании;

конфигурацию приложения через настройки.

Лучше иметь интерфейсы (UserDao, ArticleDao, CommentDao) и сервисы, которые получают зависимости через конструктор, а строки подключения хранить в конфигурации.?

7. Смешение инициализации схемы и бизнес?логики
   Метод initializeDatabase в D:

создаёт таблицы (DDL);

добавляет админа;

вызывается из main перед запуском приложения.

Инициализация схемы — самостоятельная задача, которая обычно выполняется миграциями (Liquibase/Flyway) или отдельным скриптом, а не бизнес?классом, одновременно реализующим CRUD для всех сущностей. Это снова увеличивает ответственность класса D и делает его точкой хрупкости: любое изменение схемы требует правки и переcборки приложения.?

В сумме:

Код нарушает несколько принципов SOLID (SRP, DIP), использует глобальное состояние и «божественные» классы.

Логика UI, бизнес?правила и доступ к данным тесно переплетены.

Низкая читаемость и дублирование методов усложняют сопровождение.

Для улучшения сопровождаемости рекомендовано:

выделить модель (Article, User, Comment, Role) в отдельный пакет;

разделить D на специализированные DAO?классы по сущностям;

вынести бизнес?логику в сервисы (AuthService, ArticleService, UserService, CommentService);

оставить Main только для консольного ввода/вывода и навигации по меню с использованием сервисов.
